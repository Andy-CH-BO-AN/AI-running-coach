# Continue daily coaching when Neon is unavailable

The cloud-scheduled Daily Run performs migration and coaching in one Python process. It retries Neon migration three times with 10- and 20-second backoff, then enters Degraded mode instead of failing: no later Neon read, write, engine, session, or advisory lock; a fixed ten-activity Activity window; and at most three stateless LINE notifications. Authentication, configuration, schema, and other non-transient migration failures still fail closed.

When Neon is lost after Normal mode starts, the same run enters Persistence-loss mode. Its private revocable Neon gate invalidates active handles, disposes cached engines once, and rejects every later Neon attempt locally. The already-selected 75-activity Activity window does not shrink, and notification delivery becomes stateless with a total loss budget of three. A LINE message sent immediately before its deduplication write fails consumes one slot, is not resent in that run, and leaves at most two further stateless sends. An advisory-lock release failure revokes access without issuing a second unlock query.

Mode transitions are monotonic only within one run: Normal may become Persistence-loss, while Degraded and Persistence-loss cannot recover to Normal. The next scheduled run performs a fresh migration preflight and may enter Normal again. Local, mirror, and manual workflows remain outside these Daily Run modes. We accept possible repeated notifications because GitHub Actions runners have no durable state when Neon is unavailable; adding external notification state would enlarge failure surface and operational scope.
